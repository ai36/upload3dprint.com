## 2. Архитектура

```
Браузер ── статические страницы (Astro)
   │  остров загрузки: three.js → превью, габариты, объём → цена (локально, мгновенно)
   │  файл ──PUT по подписанной ссылке──► R2 (закрытый)
   ▼
Pages Functions /api/*
   ├─ quote      — цена и срок из справочника (D1)
   ├─ upload-url — подписанная ссылка на загрузку в R2
   ├─ shipping   — тариф USPS из Портленда по весу и габаритам с упаковкой
   ├─ checkout   — создаёт Stripe Checkout Session (адрес только US, automatic_tax)
   ├─ stripe-webhook — оплата → заказ «оплачен» → письма покупателю и оператору
   ├─ status     — статус по номеру заказа и e-mail
   └─ admin/*    — список заказов, смена статуса, этикетка USPS, отмена с возвратом, справочник (за Access)
Worker `workers/cron` (Cron Trigger; у Pages Functions нет расписания) — удаление просроченных файлов (FR-015) и напоминание о сроке (SC-003). Использует те же модули из `src/`
```

### 2.0 Совместимость с обёрткой (NFR-006)
Все вызовы API идут по абсолютному адресу (`PUBLIC_API_URL`), а API разрешает CORS для origin приложения. Сайт работает из статических файлов, без серверного рендеринга. Тогда Capacitor упакует ту же сборку без правок.

### 2.1 Расширяемость (NFR-005)
- **Форматы.** `src/formats/<ext>.ts` экспортирует `parse(buffer) → BufferGeometry`. Реестр `src/formats/index.ts` сопоставляет расширение и обработчик. Новый формат — это новый файл и строка в реестре.
- **Материалы, технологии, исполнители** — таблицы D1. Новые значения — данные, код не меняется.
- **Формула цены** — `price = max(min_price, volume_cm3 × material.price_per_cm3 × qty × volume_discount(qty)) × (1 + markup)`. Коэффициенты хранятся в таблице `settings` (FR-005).

### 2.2 Геометрия и доверие к цене
Объём и габариты считаются в браузере: это быстро (NFR-001), а Worker на бесплатном тарифе не успеет разобрать файл на 100 МБ. Сервер пересчитывает цену по присланным метрикам и справочнику, но сами метрики может подделать клиент. Защита: перед передачей подрядчику оператор видит модель, и подрядчик считает свою цену по настоящему файлу. Расхождение — отмена с возвратом (P1 «Изготовление», проверка 3). См. решение D-3.

### 2.3 Внешние сервисы через переходники (решение 03.11.2026: пока без внешних аккаунтов)
Каждый внешний сервис — модуль `functions/_integrations/<сервис>.ts` с одним интерфейсом и двумя реализациями: `stub` и настоящей. Реализация выбирается переменной `INTEGRATIONS=stub|live`. Пока есть только `stub`. Настоящая реализация — отдельная задача, когда человек заведёт аккаунт. Так же исполнитель остаётся заменяемым (принцип III).

| Переходник | Интерфейс | Заглушка |
|---|---|---|
| `payments` | `createCheckout(order) → url`, `refund(order)`, разбор webhook | Страница `/checkout-stub` с кнопками «Pay» и «Decline». Они вызывают тот же обработчик webhook |
| `tax` | `calc(address, amount) → tax_cents` | Ставка из `settings` (по умолчанию 0) |
| `shipping` | `rate(parcel, zip) → {cents, days}`, `validate(address)`, `buyLabel(order) → tracking` | Тариф по весу из таблицы в `settings`, проверка формата штата и ZIP, трек-номер `STUB-<номер заказа>` |
| `email` | `send(to, template, data)` | Запись в таблицу `emails` и вывод в консоль |
| `auth` (оператор) | `isOperator(request)` | Пропускает, если `INTEGRATIONS=stub` |
| `storage` | `uploadUrl(key, size) → url`, `downloadUrl(key) → url`, `delete(key)` | URL на `/api/files/<key>`: Function пишет и читает через привязку `FILES` (локальный R2 wrangler). Настоящая реализация — подписанные ссылки SigV4 (`upload-url.ts`) |

Деплоя пока нет: всё работает локально через `wrangler pages dev`.

## 3. Модель данных (D1)

- `materials` (id, name, technology_id, price_per_cm3, colors JSON, active)
- `technologies` (id, name, min_wall_mm)
- `executors` (id, name, technology_ids JSON, build_x/y/z_mm, lead_days_min/max, pickup_address, active)
- `settings` (key, value) — наценка, минимальная цена, шкала скидок, лимит файла, сроки хранения
- `models` (id, r2_key, filename, units, bbox JSON, volume_cm3, email, expires_at)
- `orders` (id, public_no, email, address JSON, shipping_cents, tax_cents, total_cents, status, tracking_no, stripe_session_id, created_at)
- `order_items` (id, order_id, model_id, material_id, color, qty, unit_price_cents)
- `status_history` (order_id, status, at, note)
- `emails` (id, to, template, data JSON, sent_at) — журнал отправленных писем, у заглушки это единственный канал

Статусы — как в spec, раздел 2.

## 4. Сроки (принцип II, FR-006)
`срок = lead_days исполнителя + 1 день на самовывоз и упаковку + транзитные дни USPS`, показывается диапазоном рабочих дней. Верхняя граница хранится в заказе. Если заказ приближается к ней без статуса «отправлен», оператору уходит напоминание (SC-003).

## 5. Ручные шаги оператора (принцип V, SC-002)
1. Получить письмо об оплаченном заказе, передать файл и параметры подрядчику.
2. Сменить статус: передан → в печати → готов к выдаче.
3. Забрать заказ у подрядчика в Портленде, упаковать, купить этикетку из `/admin` (статус «отправлен» и трек-номер ставятся сами).
4. Отнести посылку на почту или заказать бесплатный забор USPS.
5. Отменить с возвратом, если подрядчик не может напечатать.
6. Ответить ценой на запрос ручной оценки (FR-017).

## 7. Риски
- Подрядчик поднял цену после оплаты → наценка покрывает колебание до N %. Сверх этого — отмена с возвратом. N задаётся в `settings`.
- Для USPS API нужен бизнес-аккаунт USPS.com (бесплатный). Без него — тариф по таблице из `settings`.
- Stripe Tax: 0,5 % от оборота в юрисдикциях, где продавец зарегистрирован. Регистрацию и отчётность Stripe Tax не делает.
